# SchoolPulse --- Schema Design & Database Rules

> **Purpose:** This document records the agreed first-pass database
> design for SchoolPulse, explains why the schema is structured this
> way, and gives frontend, backend, DevOps, and Data Analytics teammates
> a shared reference.
>
> **Status:** Schema design and initial validation are complete. The
> first Prisma migration has **not** yet been created or applied to
> Neon. Treat `prisma/schema.prisma` as the implementation source of
> truth; if this document and the schema diverge, raise the discrepancy
> with the Web Development Lead before changing either.

## 1. Project context

SchoolPulse is a school administration, attendance, and parent
communication platform. The MVP focuses on student records, class
management, daily attendance, parent contact records, absence
notifications, and basic announcements.

The database design is intended to support the MVP while retaining
useful history. It is not intended to implement payments, online
examinations, e-learning, payroll, biometric hardware, AI prediction, or
a full multi-school enterprise system.

### Technology

-   PostgreSQL database hosted on Neon.
-   Prisma ORM and Prisma Client.
-   Node.js, Express, and TypeScript backend.
-   Next.js, TypeScript, and Tailwind CSS frontend.
-   REST API between frontend and backend.
-   SMS and email are represented in the schema; the first notification
    implementation is email-only.

## 2. How the design was reached

The schema was designed around the MVP workflow and the Data Analytics
team's initial data domains. The first proposed domains were:

-   Students
-   Classes
-   Parents/guardians
-   Attendance
-   Notifications
-   Daily executive summaries

During review, the design added the records needed to represent real
school operations safely: academic sessions and terms, student
enrolments, teachers and historical teacher assignments, class login
accounts, admin accounts, school calendar exceptions, announcements, and
audit logs.

The guiding decisions were:

1.  **Separate real-world entities.** Students, parents, teachers,
    classes, accounts, attendance, and notifications are distinct
    records because they have different lifecycles and permissions.
2.  **Keep historical records traceable.** Where history matters,
    deactivate or end a record rather than routinely deleting it.
3.  **Use internal database IDs and separate school-facing IDs.**
    Internal `id` fields use CUIDs. IDs such as `STU-0001`, `PAR-0001`,
    and `TCH-0001` are generated by backend services and must be unique
    and never reused.
4.  **Represent changing relationships explicitly.** Student enrolments
    and teacher-to-class assignments are their own models so changes
    over time can be recorded.
5.  **Keep cross-field rules in backend validation.** Prisma's schema
    expresses fields, relations, enums, and many uniqueness constraints,
    but not every business rule can be represented by a simple schema
    declaration.
6.  **Protect references to historical data.** Relations use
    `onDelete: Restrict` so referenced records cannot be deleted while
    dependent records remain. Normal application workflows should favour
    deactivation, status changes, and audit records.

### Relationship map

``` text
Parent 1 ─── many Student
Student 1 ─── many StudentClass ─── 1 Class
AcademicSession 1 ─── many StudentClass
Teacher 1 ─── many TeacherClass ─── 1 Class
AcademicSession 1 ─── many TeacherClass
Class 1 ─── 0..1 ClassAccount
Student 1 ─── many Attendance
Class 1 ─── many Attendance
AcademicSession 1 ─── many Attendance
AcademicTerm 1 ─── many Attendance
Attendance 1 ─── many Notification attempts
Student 1 ─── many Notification attempts
Parent 1 ─── many Notification attempts
Admin 1 ─── many Announcement
Announcement many ─── many Class (through AnnouncementClass)
Admin / ClassAccount ─── many AuditLog records
```

The backend must validate that related records belong together---for
example, an attendance record's student must be enrolled in the
attendance class for the same academic session.

## 4. Student and parent/guardian records

### Student

A student has an internal `id` and a separate unique `studentId`
generated by a backend service. First and last names are required;
middle name, date of birth, gender, blood group, genotype, and admission
date are optional. Gender, blood group, genotype, and lifecycle status
use enums to avoid inconsistent free-text values.

`Student.status` describes the student's overall lifecycle: `ACTIVE`,
`INACTIVE`, `GRADUATED`, `TRANSFERRED`, or `WITHDRAWN`. It is not the
same as enrolment status for a particular academic session.

Every student must reference a parent/guardian record. Students with
attendance or other historical dependencies should not be hard-deleted
through normal app workflows.

### Parent

A parent/guardian is a separate entity because one parent can be
associated with multiple students. The student registration experience
can still be one workflow: the admin can select an existing parent or
create a new parent inline.

-   `parentId` is a unique school-facing ID generated by the backend.
-   Email is required and unique; phone is required.
-   Home address, work address, and work phone are optional.
-   `isActive` allows the record to be deactivated without removing
    historical links.
-   If an email already exists, the backend should find and
    reuse/reactivate/update the existing record as appropriate rather
    than create a duplicate parent.

If a student's assigned parent changes, update `Student.parentId`.
Future notifications use the currently assigned parent. Existing
notifications remain linked to the parent who was associated with that
delivery attempt, and the change must be audited.

Parents do **not** log in during the MVP. Their records provide contact
information for notifications and future parent-facing features.

## 5. Classes and academic calendar

### Class

A class uses a normal database model rather than a fixed enum. This
supports levels such as KG, Primary 1--6, JSS 1--3, and SS 1--3, with
optional sections such as A, B, or C.

`@@unique([name, section])` expresses the intended uniqueness. In
PostgreSQL, a composite unique constraint can still allow multiple rows
with a `NULL` section. Therefore, the backend must also prevent
duplicate sectionless class names and normalize whitespace/casing before
creation.

Classes are deactivated rather than routinely deleted. A deactivated
class cannot receive new enrolments, attendance operations, or teacher
assignments. Its history remains available.

### AcademicSession and AcademicTerm

An `AcademicSession` represents the whole academic year. An
`AcademicTerm` represents the first, second, or third term within a
session.

Agreed rules:

-   Session names are unique.
-   A session's start date must precede its end date.
-   Academic sessions must not overlap in their overall date ranges.
-   A term must fall within its session, have a valid start/end range,
    and not overlap another term in that session.
-   A fully configured session has exactly three terms.
-   Only one session is current at a time; only one term per session is
    current.
-   Different term lengths and gaps between terms are allowed.
-   Sessions and terms with historical dependent data are preserved.

These date-range and "one current" rules require backend validation and
appropriate transactional updates; the simple Prisma schema constraints
do not enforce all of them by themselves.

### SchoolCalendar

`SchoolCalendar` stores exceptions such as public holidays, mid-term
breaks, Christmas breaks, and special closures. It is not intended to
contain a row for every ordinary school day.

Each calendar entry belongs to a session and may optionally reference a
term. The schema allows only one entry per session/date. Both Super
Admins and Lower Admins can manage school-wide calendar exceptions.

Attendance creation must check the calendar and reject dates that are
not valid school days. The backend must consistently interpret dates
using the school's calendar date, not an arbitrary timestamp supplied by
a browser.

## 6. Student enrolment

`StudentClass` links a student to a class for an academic session. It
has its own status: `ACTIVE`, `COMPLETED`, `TRANSFERRED`, or
`WITHDRAWN`.

A student can have only one enrolment per academic session
(`@@unique([studentId, sessionId])`). If the student changes class
mid-session, update the existing enrolment's `classId` and create an
`AuditLog` entry describing the previous and new class. Do not create a
second enrolment for the same student/session.

This is separate from `Student.status`, which describes the student's
overall lifecycle.

## 7. Teachers and class accounts

### Teacher and TeacherClass

Teachers have profile records, but there is no individual teacher login
in the MVP. Teacher-facing access is provided through class accounts.

`TeacherClass` records a teacher's assignment to a class during a
session. Assignments have `ACTIVE` or `ENDED` status and include
assignment/end timestamps so that historical assignments can be
preserved.

Agreed rules:

-   A teacher may have at most three active class assignments at a time.
-   A class may have at most one active teacher assignment at a time.
-   Reassignment ends the previous assignment and creates a new one.
-   Teacher deactivation ends active assignments but preserves
    assignment history.
-   Teacher assignment changes must be audited.
-   Teacher phone/email are optional and must not be exposed on the
    class dashboard.

The active-assignment limits are enforced in backend logic, ideally
within a transaction. A simple unique constraint on
teacher/class/session is deliberately avoided because it would block
legitimate historical reassignments.

### ClassAccount

Each class has at most one class account. The account belongs to the
class, not to a particular teacher. When the teacher changes, the class
account remains the same.

-   Username is unique and generated from the class name by default,
    with a uniqueness fallback for collisions.
-   Passwords must be securely hashed; never store plaintext passwords.
-   Deactivating a class must also make its account unusable.
-   A deactivated class account must never be reassigned to another
    class.
-   Class-account creation, deactivation, and password resets must be
    authorized and audited.

### Admin

The `Admin` model supports `SUPER_ADMIN` and `LOWER_ADMIN`.

-   **Super Admin:** school owner's highest-level account; logs in with
    email and password; manages Lower Admins and class accounts.
-   **Lower Admin:** logs in with username and password; performs
    authorized school-management tasks but cannot manage the Super Admin
    or other Lower Admins under the agreed MVP permissions.
-   Passwords for both types are hashed.
-   Role-specific identity requirements must be enforced in the
    application: Super Admin requires an email and no username; Lower
    Admin requires a username, while email is optional.
-   Sensitive account actions must create audit records. Passwords,
    reset tokens, and other secrets must never be written to logs.

The nullable username/email columns permit both account types in one
table. Prisma does not express all conditional requirements based on
`role`, so service validation must enforce them.

## 8. Attendance: schema rules and exact user workflow

### Attendance record

Each `Attendance` row represents one student's attendance for one school
date. It references the student, class, academic session, and term.

-   Status is `PRESENT`, `ABSENT`, or `EXCUSED`.
-   `excusedReason` can be `SICK`, `LATE`, or `OTHER`.
-   `excusedReasonNote` is available for additional explanation.
-   `@@unique([studentId, date])` prevents more than one attendance row
    for a student/date, provided dates are normalized consistently.
-   Attendance must be within the relevant session and term and on a
    valid school day.
-   The backend must verify that the student was enrolled in the
    selected class for that session.
-   Admin corrections and other meaningful changes must be recorded in
    `AuditLog`.

### Status/reason validation

  -----------------------------------------------------------------------
  Attendance status       Excused reason          Note
  ----------------------- ----------------------- -----------------------
  `PRESENT`               Must be null            Must be null

  `ABSENT`                Must be null            Must be null

  `EXCUSED`               Required                Required for `OTHER`;
                                                  optional for `SICK` or
                                                  `LATE`
  -----------------------------------------------------------------------

These cross-field requirements must be validated by the backend before
saving.

### Locked attendance workflow

The agreed teacher/class-account workflow is **immediate per-student
recording**, not a separate final submission workflow:

1.  The class account opens today's attendance.
2.  The backend initializes the class's attendance records idempotently;
    students start as `PRESENT`.
3.  The teacher selects `ABSENT` for a student.
4.  The UI displays a confirmation popup asking whether the student is
    really absent.
5.  If confirmed, the backend immediately records the student as
    `ABSENT`.
6.  The absence-notification process is triggered for that attendance
    record.
7.  The teacher continues marking other students.

There is **no separate absent-student review page and no second/final
attendance submission step**. Do not add either back into the flow
without an explicit product decision.

The initialization endpoint must be idempotent: opening attendance again
should return existing records and must not create duplicates. Class
accounts can only operate on today's attendance for their own class.
Admins can view/correct any date and create missing attendance for a
previous valid school day, but cannot create future attendance.

The backend---not only the UI---must enforce class scope and
permissions. A class account must not be able to read or change another
class's attendance.

## 9. Notifications and delivery attempts

A `Notification` row represents **one delivery attempt**, not a whole
notification campaign. It links the student, the parent contacted, and
the attendance record that triggered the message.

The schema supports `EMAIL` and `SMS`. The MVP begins with email only.
Do not create fake or placeholder SMS attempts while SMS is not
implemented.

Status values:

-   `PENDING`: attempt is queued or awaiting processing.
-   `SENT`: handed off/sent to the provider; not proof of delivery.
-   `DELIVERED`: provider confirmation indicates delivery.
-   `FAILED`: attempt failed.

Agreed retry rules:

-   Maximum three total attempts per attendance/channel: the initial
    attempt plus at most two retries.
-   Retry only when the message has not been successfully delivered and
    retry policy permits it.
-   Once status is `DELIVERED`, do not retry.
-   `attemptNumber` is 1, 2, or 3.
-   `@@unique([attendanceId, channel, attemptNumber])` prevents
    duplicate attempt numbers for the same attendance/channel.
-   Provider status/webhook results determine delivery status; `SENT`
    must not be counted as `DELIVERED`.
-   Future attempts use the currently assigned parent for the student.
    Each existing attempt preserves the parent it was sent to.
-   Notification history is not hard-deleted through normal application
    operations.

The backend must validate that the student matches the attendance record
and that the notification's parent is the student's currently assigned
parent when creating a new attempt. Provider secrets and credentials
must never be stored in schema fields or audit descriptions.

## 10. Announcements

An `Announcement` is created by one admin. It can be school-wide or
targeted to specific classes. `AnnouncementClass` is the join model for
targeted classes and prevents the same class from being attached twice
to the same announcement.

Agreed rules:

-   Super Admins and Lower Admins can create and publish announcements
    directly; no approval workflow is required.
-   Draft: `isPublished = false` and `publishedAt = null`.
-   Published: `isPublished = true` with `publishedAt` set.
-   Editing an already published announcement does not reset its
    original `publishedAt`.
-   School-wide announcements (`isSchoolWide = true`) must have no class
    targets.
-   Targeted announcements (`isSchoolWide = false`) must have at least
    one class target.
-   The creator is preserved even if that admin is later deactivated.
-   Meaningful changes are audited.
-   Published announcements are not hard-deleted through normal app
    operations.

The cross-field publication and targeting rules require service
validation.

## 11. Audit logs and historical integrity

`AuditLog` records important actions with an action name, entity type,
entity ID, optional description, timestamp, and actor reference. The
actor can be an admin or class account; the application must ensure
exactly one actor is populated for each authenticated action.

Important audited operations include:

-   Attendance corrections.
-   Student class changes.
-   Parent/guardian changes.
-   Teacher assignment, reassignment, and deactivation changes.
-   Admin/class-account creation, deactivation, and password resets.
-   Announcement changes.

Never include plaintext passwords, reset tokens, provider credentials,
or other secrets in an audit entry. Audit logs are append-only through
normal application workflows; they should not be edited or deleted by
routine features.

The explicit `onDelete: Restrict` relation actions protect referenced
records from being deleted while dependent rows exist. Use lifecycle
status fields and end dates instead of routine hard deletion where
history matters.

## 12. What Prisma enforces vs. what the backend must enforce

### Expressed in the schema/database

-   Required vs. optional fields and enum values.
-   Internal primary keys and unique school-facing IDs.
-   Unique parent email and unique teacher email when supplied.
-   Unique class account username and one class account per class.
-   One student enrolment per session.
-   One attendance row per student/date, assuming normalized dates.
-   One notification attempt number per attendance/channel.
-   One announcement-class link per announcement/class.
-   One calendar entry per session/date.
-   Foreign-key relationships and `onDelete: Restrict` protections.
-   Common lookup indexes.

### Must be enforced in backend validation, authorization, or transactions

-   Role-specific identity requirements for `Admin`.
-   Password hashing and authentication/authorization.
-   Class-account access limited to its own class.
-   Teacher limit of three active classes and one active teacher per
    class.
-   Only one current academic session and one current term per session.
-   Session/term date ranges, overlap prevention, and term/session
    consistency.
-   Exactly three terms for a fully configured academic session.
-   Duplicate sectionless class prevention and class-name normalization.
-   Attendance status/reason/note combinations.
-   Attendance date validity, school-calendar checks, and enrollment
    consistency.
-   Idempotent attendance initialization and prevention of duplicate
    attendance creation.
-   Admin vs. class-account date permissions.
-   Notification/student/attendance/parent consistency, retry limits,
    and delivery transitions.
-   Announcement publication and school-wide/class-targeting
    consistency.
-   Exactly one audit actor for an authenticated action.
-   Generating unique `STU-`, `PAR-`, and `TCH-` IDs and usernames.
-   Creating audit entries for important changes.

Where a rule spans multiple records, use a database transaction where
appropriate to avoid race conditions. Do not rely on frontend checks
alone for permissions or business rules.

## 13. Implementation and migration workflow

The current backend uses Prisma 7 configuration in `prisma7.config.ts`;
the datasource URL is supplied through environment configuration rather
than embedded in `schema.prisma`.

### Neon connection URLs

Use separate environment variables for runtime queries and Prisma CLI
operations:

-   `DATABASE_URL`: pooled Neon connection string (the hostname contains
    `-pooler`). The backend's Prisma driver adapter uses this at
    runtime.
-   `DIRECT_URL`: direct, non-pooled Neon connection string (the
    hostname does **not** contain `-pooler`). Prisma CLI commands such
    as migrations should use this URL.

Configure `prisma7.config.ts` to read `DIRECT_URL`, for example:

``` ts
import "dotenv/config";
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
  },
  datasource: {
    url: process.env["DIRECT_URL"],
  },
});
```

Your local `.env.example` should document both variables with
placeholders. Put the actual connection strings only in your local
`.env` or the appropriate deployment secret settings. Never commit or
paste the actual credentials. Obtain the direct URL from Neon by opening
the project's connection details and disabling connection pooling before
copying the connection string.

### Before creating the first migration

1.  Confirm the checked-in `prisma/schema.prisma` contains the approved
    fields, relations, indexes, unique constraints, and explicit
    `onDelete: Restrict` actions.

2.  Confirm local `.env` contains both `DATABASE_URL` and `DIRECT_URL`,
    and remains untracked.

3.  Confirm `src/config/prisma.ts` uses `DATABASE_URL` for the runtime
    adapter and `prisma7.config.ts` uses `DIRECT_URL` for Prisma CLI
    operations.

4.  Run:

    ``` bash
    npx prisma format
    npx prisma validate
    npm run build
    ```

5.  Review the final schema with the Web Development Lead, DevOps, and
    Data Analytics representatives.

6.  Create the first migration only after approval. Review the generated
    SQL before applying it to the Neon database. If Prisma asks to reset
    the database or the command reports unexpected existing objects,
    stop and investigate rather than approving a reset.

7.  Commit both `prisma/schema.prisma` and the generated migration
    directory. Do not edit an already shared migration casually;
    coordinate schema changes through a new migration and PR.

8.  Regenerate Prisma Client as needed and verify a real database
    connection.

The schema validation and TypeScript build have passed in the
development environment. At the time this document was prepared, the
Neon database had no Prisma migration history and the first migration
was still pending.

## 14. Team coordination expectations

-   **Backend:** implement validation, transactions, access control,
    notification state transitions, and audit writes described here.
-   **Frontend:** follow the locked attendance workflow and show only
    actions allowed for the current role.
-   **DevOps:** protect database credentials, manage environment
    variables, and coordinate migration application across environments.
-   **Data Analytics:** align field names and status semantics with this
    schema. Derive summary metrics from detailed attendance and
    notification records unless a separate summary table is explicitly
    agreed later.
-   **All contributors:** propose schema changes through the normal PR
    process. Before adding or renaming a field, check this document, the
    current Prisma schema, API contracts, and analytics expectations.

## 15. Key design trade-offs to remember

-   The schema intentionally keeps parent records separate from students
    so siblings can share a parent.
-   `StudentClass` and `TeacherClass` preserve academic enrolment and
    assignment history instead of overwriting all history into the
    student/class/teacher rows.
-   `ClassAccount` belongs to a class, not a teacher, so teacher changes
    do not require changing the class login.
-   Attendance is recorded immediately after the per-student absence
    confirmation; there is no final attendance submission stage.
-   Each notification row is one attempt so delivery and retry history
    can be measured accurately.
-   Status fields preserve important records instead of routine hard
    deletion.
-   Some rules are application-level because simple Prisma declarations
    cannot express every conditional or multi-record invariant.
